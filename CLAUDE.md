# BRUTEFORCE 3D 2.0 — рабочая памятка

Браузерный автобаттлер. Игрок собирает персонажа, отправляет в рейд, смотрит
бой. В бой не вмешивается — значит вся глубина живёт **до** боя.

Читать перед работой: `docs/GDD-2.0.md` (дизайн), `docs/adr/0001-stack.md`
(почему такой стек), `docs/ART-BIBLE.md` (2D-ассеты).

**Раздел 12 GDD — аудит версии 1.0.** Это список того, что нельзя повторить.
Если решение похоже на что-то оттуда, оно неверное.

---

## Незыблемые инварианты

Не рекомендации. Решение, противоречащее любому пункту, не обходится —
о нём сообщают человеку.

1. **Клиент никогда не пишет в БД.** Ни одной таблицы, ни при каких условиях.
   Все записи — через серверные эндпоинты, которые читают состояние игрока
   **из базы**, а не из тела запроса. Главный урок v1.0: там золото и предметы
   правились из devtools.
2. **`packages/sim` — чистая функция.** Ноль зависимостей, ноль I/O, ноль
   обращений к сети и времени. Никакого `Math.random()` и `Date.now()` —
   только сид аргументом. Один сид → побитово идентичный результат.
3. **`packages/sim` не попадает в браузерный бандл.** Симуляция только
   на сервере. Превью шансов — эндпоинтом `POST /simulate/preview`.
4. **Механики без теста не существует.** У каждого трейта, статуса и формулы —
   тест, доказывающий, что поведение совпадает с описанием. В v1.0 шесть
   трейтов из семнадцати описывали одно, а делали другое.
5. **Числа баланса — в данных, не в коде.** Всё в `packages/data/balance.json`.
   Коэффициент, захардкоженный в логике, — это баг.
6. **Все пользовательские строки — в `locales/{ru,en}.json`.** RU основной.
   Захардкоженный текст в UI — баг.
7. **Секреты не коммитятся.** `.env` в `.gitignore`, `.env.example`
   в репозитории, реальные значения — в переменных окружения Render.

## Правила работы с документами

Из патча 2.0.1, соблюдать:

1. **GDD не содержит имён вендоров.** Только «сервер», «база», «эндпоинт».
2. **Решения о стеке — в `docs/adr/`.** Пронумерованные, с датой и причиной.
3. **Агенты не редактируют GDD.** Нашли противоречие — сообщают, правку
   вносит человек. `docs/` исключён из Prettier, чтобы автоформат не
   считался правкой.

## Команды

```bash
pnpm install

pnpm dev              # сервер :8787 и клиент :5173 параллельно
pnpm lint             # ESLint
pnpm typecheck        # tsc --build по всему репозиторию
pnpm test             # Vitest
pnpm build            # пакеты, сервер, клиент
pnpm check:bundle     # движка и секретов нет в собранном клиенте
pnpm format           # Prettier (docs/ не трогает)

pnpm db:generate      # схема изменилась -> новая миграция. Офлайн
pnpm db:migrate       # применить. Нужен DATABASE_URL

pnpm db:local:up      # локальный Postgres 16 на :55432
pnpm db:local:psql
pnpm db:local:down
```

**Локальная база нужна не для удобства.** Из этой среды разработки может
не быть сети до Neon: политика egress закрывает `console.neon.tech`,
`api.neon.tech`, `api.render.com` и прямой TCP на 5432. Проверить
`curl -sS "$HTTPS_PROXY/__agentproxy/status"`. Обходить блокировку нельзя;
если Neon недоступен — работать на локальном Postgres, схема и миграции
там те же самые.

## Как устроены границы

**Инвариант 3 держат четыре независимых рубежа.** Каждый по отдельности
обходится, вместе — нет:

1. правило ESLint на импорт `@bruteforce/sim` из `apps/web`;
2. `@bruteforce/sim` отсутствует в зависимостях `apps/web`;
3. плагин Vite `bruteforce:forbid-sim-import` падает на резолве;
4. `scripts/check-bundle.mjs` ищет в собранном `dist` маркер движка,
   `postgres://`, `neon.tech`, `BETTER_AUTH_SECRET`.

**Инвариант 1 держится тем, что у клиента нет пути к БД:** нет роли, нет
строки подключения, нет эндпоинта, принимающего игровое состояние. Идентификатор
игрока берётся только из проверенной сессии (`requireSession`), профиль
читается из БД. Роль приложения (`server/sql/grants.sql`) не может ни
`CREATE`, ни `ALTER`, ни `TRUNCATE`, ни трогать журнал миграций.

**Инвариант 6 держится тем, что сервер отдаёт ключи, а не текст.** В теле
ошибки — `messageKey` и `fields` с ключами локалей. Английские строки zod
наружу не уходят: их превращает в ключи `fieldErrorKeys`.

Сделано: монорепо, схема БД (12 таблиц), авторизация, регистрация

Дальше по GDD §10 — **M1: боевой движок.** Порядок этапов не переставляется.

### Что осталось незакрытым

- **Миграции на Neon не применялись.** Схема проверена только на локальном
  Postgres 16. Причина — блокировка egress, см. выше.
- **`plan: free` в `render.yaml`.** ADR 0001 говорит, что нужен starter,
  и это верно — free засыпает после 15 минут. Для M0 выбран free сознательно;
  апгрейд — отдельное решение человека.
- **Профиль создаётся не в одной транзакции с учётной записью.** Better Auth
  не отдаёт свою транзакцию. Строка `players` создаётся хуком сразу после
  учётной записи, а `GET /me` достраивает её, если хук не отработал.
  `ensurePlayer` идемпотентен, `players.user_id` уникален.
- **§10 GDD, строка про M0** всё ещё упоминает RLS. Патч 2.0.1 её не
  затрагивал, а сам GDD агенты не правят. Вопрос к человеку.
- **Ветка Neon на PR** не настроена: нужен `NEON_API_KEY` в секретах
  репозитория. CI использует Postgres в контейнере — для проверки миграций
  этого достаточно.
