## Правка 3 — §2.1, абзац про переиспользование движка (строка 65)

**Было:**
```
**Критично:** `packages/sim` компилируется и для Deno (сервер), и для браузера
(клиент). Один и тот же код, одно и то же поведение. Клиентская копия
```

**Стало:**
```
**Критично:** `packages/sim` исполняется только на сервере и никогда не
попадает в браузерный бандл. Причины три: одна реализация правды вместо двух
расходящихся, меньше вес клиента, и движок не лежит у читера в devtools.

Превью шансов победы клиент получает эндпоинтом `POST /simulate/preview`,
а не считает у себя. Сборка клиента падает, если `packages/sim` оказался
в графе зависимостей `apps/web`.
```

## Правка 5 — §2.3, абзац про RLS (строка 121)

**Было:**
```
RLS: клиент имеет `SELECT` на свои строки и на публичные (лидерборд, реплеи).
**`INSERT`/`UPDATE`/`DELETE` для клиента запрещены полностью** — только
service role внутри Edge Functions.
```

**Стало:**
```
**У клиента нет доступа к базе данных вообще.** Ни на чтение, ни на запись,
ни через какую роль. Соединение с БД существует только внутри серверного
процесса. Клиент получает данные исключительно через HTTP-эндпоинты, которые
сами решают, что ему показать.

Это строже, чем разграничение прав на уровне БД: там всегда остаётся
соблазн «здесь-то клиенту можно напрямую», и ровно так родилась дыра v1.0.
```

# Файл `docs/adr/0001-stack.md`

Создать новый:

```markdown
# ADR 0001 — Хостинг и стек

**Дата:** 2026-08-17
**Статус:** принято

## Контекст

GDD 2.0 писался с расчётом на Supabase Edge Functions. После того как был
зафиксирован сервер-авторитет, выяснилось, что половина преимуществ Supabase
для нас не работает.

## Решение

Render (сервер и статика) + Neon (Postgres) + Hono + Drizzle + Better Auth.

## Почему не Supabase

- **RLS перестаёт быть преимуществом.** Его смысл — безопасно пускать клиент
  писать напрямую. Мы решили не пускать. RLS сводится к «клиенту всё
  запрещено», и остаётся соблазн сделать исключение — как в v1.0
- **Realtime не нужен.** Арена асинхронная, бой считается одним вызовом
- **Долгоживущий процесс лучше edge-функции.** Движок — чистый TS без I/O.
  На тёплом Node нет холодных стартов и лимитов CPU, а географическая
  близость к пользователю нам безразлична: регион один
- **Neon даёт ветвление базы** на каждый PR. Для проекта с частыми
  миграциями схемы предметов это существенно

## Цена решения

Теряем встроенную авторизацию — закрывается Better Auth.
Render Web Service на Free засыпает после 15 минут простоя, нужен
Starter ($7/мес). Это не опционально.

## Следствия

- Строка подключения к Neon — **pooled**, не прямая
- `packages/sim` исполняется только на сервере (см. GDD §2.1)
```

# Правило на будущее

1. **GDD не содержит имён вендоров.** Только «сервер», «база», «эндпоинт»
2. **Решения о стеке — в `docs/adr/`.** Пронумерованные, с датой и причиной.
   Через три месяца никто не помнит, почему не Supabase, и спор начинается заново
3. **Агенты не редактируют GDD.** Нашли противоречие — сообщают, правку
   вносит человек. Документ, который агент правит сам, перестаёт быть
   заданием и становится его же черновиком
